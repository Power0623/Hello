# Luma 新版与账号开通说明

## 本次改动

- 本地版本的名字改为“闫圣强”；登录账号初始不使用站主姓名，每人可以填写自己的名字。
- 日期和问候语随当天时间变化；首页选取今天及之前尚未完成的前三条任务。
- 任务支持新增、编辑、计划日期、自定义分类、搜索、完成、删除及撤销。
- 习惯支持新增、编辑、按真实日期打卡、跨周查询和归档，连续天数实际计算；禁止未来打卡。
- 目标支持新增、编辑、截止日期、精确百分比、完成状态、归档和恢复。
- 专注支持选择 5/15/25/45/60 分钟、暂停继续、重置、刷新恢复及后台时间校准；完成后写入真实记录。
- 周报使用实际完成时间、专注记录和打卡记录，不再显示虚构数值。
- 设置支持姓名修改、JSON 导出、导入预览、确认替换前备份。
- 旧版任务、习惯和目标迁移至新数据格式。原 `luma-data` 保留不覆盖；无日期的旧勾选单独保留，不计入真实周报。
- 账号功能代码包含邮箱验证登录、退出、按账号读写、数据库行级权限与版本冲突检查。

**当前状态：账号代码已接入，但空配置时仍为本地版本。必须完成以下项目配置并通过真实登录测试，才算账号功能开通。**

## 部署分工

| 服务 | 作用 |
| --- | --- |
| GitHub Pages | 托管公开网页，继续使用 https://power0623.github.io/Hello/ |
| Supabase Auth | 验证邮箱、建立用户身份、管理登录会话 |
| Supabase Postgres | 保存每个账号的数据，用行级安全策略阻止跨账号读写 |
| 自定义 SMTP 发信服务 | 向普通用户发送登录邮件 |

GitHub 仓库不保存用户任务、邮箱列表或登录密码。网页内只配置可公开的服务地址和 publishable key；数据库在服务端根据登录身份检查访问权限。

这里的“一人一账号”按唯一邮箱身份实现，并非身份证实名核验；同一个邮箱可以在多个设备登录。

## 1. 创建 Supabase 项目

1. 打开 https://supabase.com/dashboard ，使用 GitHub 登录。
2. 创建自己的组织和项目，项目名称可填 `luma`；按实际用户位置选择可用区域。
3. 数据库密码由自己设置并保存，不要填写进网页代码或聊天。
4. 等项目准备完成，找到 Connect 或项目 API 设置中的 Project URL 和 Publishable key。
5. 将这两项公开配置填入本地 `public/luma-config.json`：

```json
{
  "supabaseUrl": "https://你的项目编号.supabase.co",
  "supabasePublishableKey": "sb_publishable_你的公开配置"
}
```

只接受以 `sb_publishable_` 开头的新公开密钥。`sb_secret_`、service_role、数据库密码和个人管理令牌均不能写进此文件，也不能上传到公开仓库。

## 2. 初始化数据库和访问权限

在自己的 Supabase 项目内打开 SQL Editor，运行本项目 `supabase/schema.sql` 的完整内容。

脚本创建：

- `luma_states`：每个用户一行，存储自己的结构化记录和修订号。
- RLS 策略：只允许登录身份对应的 `user_id` 读写，不给匿名访客表访问权限。
- `luma_save_state`：核对当前用户和调用方预期用户，按修订号保存；修订号不一致时拒绝覆盖。

网页不能自行初始化数据库。未运行 SQL 就填入账号配置，会导致账号登录后无法读取记录，网页会显示错误并停止操作，不会回退为一个看似同步成功的空账号。

## 3. 设置登录邮件和回跳地址

在 Authentication 的 URL Configuration 中设置：

- Site URL：`https://power0623.github.io/Hello/`
- Redirect URLs：加入同一个完整网址。仅在开发测试需要时另外加入 `http://localhost:3000/`。

邮箱验证登录默认可使用 magic link。若希望用户直接输入验证码，在 Authentication 的邮件模板中，将 Magic Link 模板加入 `{{ .Token }}`，例如：

```html
<h2>Luma 登录验证码</h2>
<p>你的验证码为：{{ .Token }}</p>
<p>如果不是你本人操作，请忽略这封邮件。</p>
```

保持邮箱验证开启。用户第一次成功验证邮箱时自动建立身份，无需自行保存密码。

## 4. 给其他用户发邮件

Supabase 的默认邮件服务仅用于受限测试，只能给项目团队内的预授权地址发送邮件，并有较低发送限额。让普通朋友注册前，需要在 Authentication 中配置自定义 SMTP。

在所选发信服务完成账号和发信地址/域名验证后，将 SMTP 主机、端口、用户名、密码、发件人配置在 Supabase 控制台。SMTP 凭证只留在服务端，不写进本项目。

如果暂时不想配置邮件服务，也可以后续改接 GitHub 等第三方登录；这需要在相应平台创建 OAuth 应用，当前版本尚未实现该入口。

## 5. 开通前验收

1. 当前未开通账号时，先在网页“设置”中导出旧记录。
2. 运行数据库脚本，配置邮件与回跳地址，再发布公开配置文件。
3. 使用账号 A 登录，填写姓名、新增任务并等待“已保存到云端”。
4. 在另一浏览器登录账号 B，确认初始为空，不能看到 A 的内容。
5. 在另一设备登录 A，确认可读取 A 的数据；通过“设置”导入预览确认旧记录。
6. 在两台设备分别修改同一份旧版本数据，确认后保存的过期版本提示冲突，不覆盖先保存的版本。
7. 退出账号，确认业务页面不再展示；确认未登录的数据访问被拒绝。
8. 模拟网络中断，确认保存失败显示提示，并能导出当前未保存内容。

这些实际云端验收需要配置完成，不能由本地测试替代。

## 本地验证

- `pnpm test`：日期、迁移、统计、备份、计时与云接口调用逻辑测试。
- `pnpm test:security`：在内存 PostgreSQL 中运行相同建表及权限脚本，模拟两个用户与未登录访客，验证数据隔离和版本冲突。
- `pnpm build:pages`：构建 GitHub Pages 静态发布文件。

GitHub Pages 发布目录为 `github-pages-dist/`，包含 `index.html`、`luma-config.json`、图标、分享图片及 `.nojekyll`。发布必须包含配置文件；源码改动不会自动成为线上版本。

## 当前边界

- 同一账号跨设备能读取云端数据，但尚无实时推送和字段级自动合并；进入编辑前建议重新载入，冲突时先导出再加载云端。
- 进行中的计时器在发起它的浏览器保存，完成结果同步到账号。跨设备不会共同控制一个正在运行的倒计时。
- 仅完整结束的专注轮次计入周报；重置的轮次不计入。
- 习惯目前每天一次，暂不支持每周次数或数量型打卡。
- 目标目前手动调整进度，暂不自动关联任务、里程碑。
- 任务计划日期按用户浏览器本地日期解释；完成时间以时间戳保存，周报按查看设备本地时区计算。
- 删除任务为软删除，保留已完成的历史统计。取消完成则撤回该任务的完成统计。
- 本地旧数据不会自动上传到任意新账号；必须在设置里预览并确认归属后导入。
